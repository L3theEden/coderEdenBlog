## 一、它先装作只是慢了一点

那天晚上我在阿里云上更博客。事情本来很短：传新的 `.mdx`，跑 `npm run build`，然后把服务拉起来。

终端停在这里：

```bash
[build] Building static entrypoints...
```

这种停顿最坏。它不像报错。它给你一种错觉，好像只是慢一点，再等一会儿就好了。

于是我真的等了一会儿。

几分钟过去，提示符没回来。页面没更新。机器越来越钝。我还在想，是不是 Astro 这次构建重一点，是不是新文章大了点，是不是服务器今晚状态差。人在这种时候很喜欢替系统找借口，因为那比承认“有东西卡死了”轻松。

## 二、我先怀疑了所有新东西

我先去看新加的 `.mdx`。怀疑 frontmatter。怀疑引号。怀疑是不是哪里少了一个闭合标签。后来又去看 `astro.config.mjs`，像所有出事故的人一样，先翻最近动过的地方。

都不是。

真正的问题一点都不新。是旧东西没走。

前一次部署留下来的进程还活着，站点还挂在那里。我没有先停它，就直接在原地重新 build。新的 `npm run build` 看起来像在工作，其实只是被吊住。屏幕上那句 `Building static entrypoints...` 一直亮着，像一种礼貌的沉默。它没有告诉我哪里错了。它只是不给我结束。

> 很多时候，把机器拖垮的不是一个新 bug，而是一个本该先结束、却没有结束的旧进程。

## 三、真正糟糕的是它不吵

这次最坏的地方，不是它报了一个很响的错。恰好相反，它太安静了。

命令卡着。资源慢慢涨。你还能敲点别的东西，但整个系统已经开始发黏。等我反应过来不对，服务器已经快没余地了。后面就没什么可描述的了，整台机器失去响应，我只能重启。

重启以后反而更难受。因为一切都很普通。服务得重新拉。网页还是旧的。刚才那段漫长的等待没有换来任何结果，只留下一个很蠢、但又没法否认的事实：我把部署顺序搞反了。

## 四、以后不靠记忆

这件事之后，我给这个博客的部署只留一套动作，不再临场发挥：

```bash
pm2 stop codereden
npm run build
pm2 restart codereden
```

如果我怀疑缓存和旧产物也在搅局，就多加一步：

```bash
pm2 stop codereden
rm -rf dist .astro
npm run build
pm2 restart codereden
```

就这些。没什么高明的。

先让旧进程退场，再生成新东西。顺序不能反。反了就会出事。不是每次都出大事，但早晚会有一次让你长记性。

## 五、把顺序写下来，比记住它更重要

后来我一直觉得，这件事其实不值得上升成什么“部署哲学”。它更像一种手工活里的常识。只是常识一旦不写下来，到了凌晨就会失效。

我们总以为自己记得住那些简单步骤。可真正到线上，页面没更新，终端卡着，心里一烦，顺序就乱了。乱掉以后，问题也不会自动变复杂，它只是继续待在那里，看你多付一点代价才肯走。

这次代价不算大。重启之后服务还能起来，文章也没丢。但我还是想把它写进博客。不是因为这件事有多传奇，恰恰因为它一点都不传奇。

旧进程不退出，新构建就会卡住。  
如果你非要等它自己好，最后卡住的通常不止构建。
