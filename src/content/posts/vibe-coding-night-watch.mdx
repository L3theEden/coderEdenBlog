## 一、工作坊里真的着过火

这次博客项目，某种意义上，确实是 vibe coding 出来的。

我把设计稿、计划、约束、目录结构丢进去，另一头开始吐命令、写文件、跑 build、补页面、提交 commit。它先 `/init`，再读 spec，再写 `CLAUDE.md`，然后一路往下推。中间还会自己说：“我需要先调用执行计划的 skill 来了解执行规范。”

那一刻我有一种很奇怪的轻松。像你在深夜搬东西，忽然有人从楼梯拐角伸手，替你托住了箱子的一边。

于是事情真的往前走了。

```bash
git init
git branch -m main
npm install
npm run build
npm run check
npm run preview
```

这些命令今天看起来平平无奇。可当另一个东西替你把它们一行一行接过去的时候，手心会发热。

## 二、火快得不像是人间的速度

让我愣住的不是它会写页面，而是它会继续。

它写完一个 `index.astro`，不邀功，接着往后推。Task 1。Task 2。Task 3。中间依赖冲突了，继续试。`astro@^5` 跟新版生态不合，退回兼容版本。构建过了，继续提交流水。断了一次会话，重读记录，再接上 Task 12 到 Task 18。最后把 `/rss.xml`、`/404.html`、`/series/[series]`、`/tags/[tag]` 一路补齐。

说实话，这种感觉很容易让人上瘾。

因为它给你推进感。下一步该干什么，它不告诉你，它直接做。人很难不对这种速度动心。尤其是在一个还没完全开始的项目里，你本来面对的是一整张空白桌面，现在忽然有人替你把木板、钉子、火柴、灯都摆好了。

> vibe coding 最危险的地方，是那种好像可以放心交出去的流畅。

人会被流畅骗到。

## 三、火苗最亮的时候，最容易忘记谁在看守

这份对话里，我最喜欢的细节是那些卡住的地方。

比如一开始它写下 "The repo has not been bootstrapped yet." 可后来仓库真的被一步步 bootstrap 了。比如装依赖时撞上版本冲突，最新的 `@astrojs/mdx` 要 Astro 6，`@astrojs/tailwind` 又不认 Astro 6，于是只好折回去找一组能活下来的版本。比如旧会话断掉以后，它还得先读命令记录，确认任务做到哪里，再继续。

这些地方让我反而安心。

因为模型犯错并不可怕。可怕的是它一路顺滑，顺滑到你开始不想看了。你会想：“它都完成 11 个任务了，后面应该也没问题吧。”你会想：“build 都过了，页面也能打开，这事算结束了吧。”

可工程从来不是这样结算的。

build 通过，不等于东西就是对的；站点跑起来，也不等于这团火以后不会烧到别的地方。

## 四、守夜这件事，没有被自动化掉

我越来越觉得，所谓 vibe coding，写得诚实一点，远没有“我一句话，项目自己长出来了”那么神。它更像这样：

我先给出一份设计、一份计划、一堆约束，模型替我扛走大部分体力活和一部分判断活。但网站要长成什么样、哪些偏差可以接受，仍然是我的事；它跑偏的时候，把它拽回来的也是我。最后署名的，还是我。

这才是让我后背发紧的地方。火确实被偷来了。可普罗米修斯没有替凡人发明消防队。

工具今天已经能把一整个博客从“还只有文档”推到“本地预览跑起来”。这件事很厉害，也很不安。因为从今天开始，工程师多了一个很具体的职责：坐在工作坊边上，确认火盆没翻。

以前我们说 review、测试、验收。现在这些词都还在，只是重量变了：从流程末尾的盖章，变成一份证词——证明火烧起来的时候，你没有离开桌边。

## 五、localhost:4321 亮起来的时候

最后它把预览服务跑起来了。

屏幕上出现一句话：

`Preview server is up at http://localhost:4321/.`

我看着那行字，居然没有太兴奋。更多的是一种安静。像你在深夜把最后一块木板钉好，退后半步，看见屋里终于亮灯。灯不是你一个人点的，但你知道，今晚不能没人守着。

我想，以后我还是会继续这样做。继续让模型写，继续让它跑，继续把那些本来会拖我两小时的样板、胶水和重复工序交给它。否则就太浪费这团火了。

但我也想记住这一次。

记住一个项目是怎么在长对话、命令输出、依赖报错和一串 commit 里慢慢成形的。记住那种很容易让人误会成“自动完成”的流畅。记住流畅退潮之后，最后留在桌上的那件事。

是守夜。
