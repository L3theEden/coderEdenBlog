对应主文：[《动手以前，先照亮房间》](/blog/prometheus-light-the-room/)。

主文写动手前的停顿。这篇把停顿拆成工程动作：当前允许做什么，下一步需要什么证据，以及谁来判断证据是否充分。

以下以《这 7 个 AI 编程提示词，建议直接收藏！》为起点，保留七个场景，补写执行条件和验收要求。模板是扩写版本；代码是独立教学示例。它们适用于能够读取仓库、修改文件和运行命令的编程 Agent，按任务选用即可。

提示词表达的是协作意图。必须执行的检查，应接入 CI 等实际机制；文件和命令权限也要由工具配置约束。Anthropic 的官方文档同样区分模型读取的指令与工具层执行的控制，单靠强调措辞没有强制效果。[参考：Claude Code 文档](https://code.claude.com/docs/en/best-practices#deterministic-and-non-deterministic-instructions)。

## 一、读清现状，再决定改哪里

适合需求含糊、跨模块修改，或者刚进入陌生仓库的情况。要产出的东西是有依据的改动方案，阅读范围应围绕任务收敛。

```text
本轮先不修改代码。
阅读与需求有关的代码、测试、配置、依赖声明和相邻实现，
遵守仓库约定，找到可复用的逻辑。

用自己的话复述目标，列出关键假设、对应的文件依据、
最小改动范围和验证方法。
只有仓库找不到答案、且答案会影响方案选择时，才向我提问。
本轮交付方案，等我确认后再进入实现。
```

验收时，检查它是否指出了具体入口和相邻实现。例如“沿用现有 CSV 序列化函数”，比“遵循项目风格”更有信息量。再检查验收条件有没有歧义：空列表应下载带表头的文件，还是应禁用导出按钮？代码库未必能替产品决定这件事。

“等我确认”用于明确约定的方案阶段。若任务已经获准执行、范围清楚，就不必每走一步重新询问；约定只在出现影响方案的缺失信息时停下即可。

## 二、把最小改动落到具体范围

“最小”要同时满足需求、现有约定和必要的可靠性要求。可以用修改范围判断，也要看是否额外引入了依赖、抽象层或维护负担。

```text
按已确认的需求做最小充分改动。
先参考相邻实现，复用项目现有逻辑，不为假想的未来需求增加抽象。
不顺手重构无关代码，不引入完成本任务不需要的依赖。

保留契约要求和实际输入边界上的校验、错误处理。
若必须扩大改动范围，先说明具体原因。
交付时列出修改文件，并说明每项修改对应哪个需求。
```

给导出按钮修一个空列表分支，通常不需要同时建立“多格式导出插件系统”。但来自外部的输入、确实可能超时的请求，仍然需要按项目契约处理。原文的“不要处理实际不会发生的错误”，需要有证据支持“不会发生”。

Google 的审查指南把为尚不存在的需求提前泛化列为过度设计，也要求检查改动是否与现有系统相容。[参考：Complexity 与 Design](https://google.github.io/eng-practices/review/reviewer/looking-for.html#complexity)。

对错字、静态文案等低影响修改，直接检查结果往往已足够。不要为了执行模板，先给项目装一套用不上的测试框架。

## 三、修 Bug：让同一个用例先失败，再通过

复现把“看起来像某个问题”变成可观察的失败。失败原因必须对应报告的缺陷；缺依赖、文件路径错误导致的测试失败，都不能充当复现证据。

```text
先定位并复现问题，暂不修改生产代码。
优先在现有测试框架中写一个最小用例，或给出可重复执行的复现脚本。
明确输入、前置条件、期望结果和实际结果。

确认旧实现因目标缺陷失败后，根据调用路径和运行证据定位根因，
再做最小修复。保留同一个回归用例，验证修复后通过。
报告执行命令及失败到通过的结果，不要修改断言来迁就错误行为。
若无法复现，说明缺失条件和已排除的假设。
```

假设约定是“空列表也要导出表头”。把下面的独立示例存为 `csv-repro.test.mjs`：

```js
import assert from 'node:assert/strict';
import test from 'node:test';

function toCsv(rows) {
  if (rows.length === 0) return ''; // 待复现的错误
  return ['name', ...rows.map((row) => row.name)].join('\n') + '\n';
}

test('空列表仍保留 CSV 表头', () => {
  assert.equal(toCsv([]), 'name\n');
});
```

用 `node --test csv-repro.test.mjs` 执行。断言应指出实际值为空字符串，期望值为 `name\n`。删除提前返回空字符串的那一行，再运行同一条命令，用例应通过。

示例在 Node.js 26.0.0 上验证，使用内置的 [`node:test`](https://nodejs.org/api/test.html)。它只演示空列表缺表头的分支，没有实现完整 CSV 转义；生产代码应复用项目已有的序列化器，并覆盖逗号、引号等输入。

并发、设备或网络相关问题，可能无法立刻稳定复现。此时可以先固定随机种子、记录事件次序，或在可控环境注入故障；仍然无法重现的部分，要保留为未验证项。反复运行直到偶然通过，无法说明根因已消失。

## 四、重构：先建立旧行为的基线

重构的约束是保持外部可观察行为，同时调整内部结构。这与修复缺陷的目标不同。[参考：Martin Fowler 对重构的定义](https://martinfowler.com/bliki/DefinitionOfRefactoring.html)。

```text
先不重构，先识别本次修改影响的公开行为和依赖方。
利用现有测试，并补充关键路径与已识别边界的特征测试。
测试需在原实现上通过；断言外部可观察行为，尽量不绑定内部结构。

列出暂未覆盖的行为，以及看似异常但可能已被依赖的历史行为。
建立通过的基线后，小步重构，每步运行相关测试。
若需要改变行为，单独说明并作为行为变更处理。
```

特征测试（characterization tests）记录现有程序实际表现。它能保留兼容性线索，却不能自动证明这些表现符合需求。旧代码把空列表导出为空文件，特征测试可以记录这一事实；若约定要求表头，就应另建缺陷用例并修复，不能永久把错误当作正确结果。

原文说“固定当前所有行为”。实践里很难证明已穷尽所有输入与状态，更可执行的要求是明确覆盖范围：关键输出、错误类型、必要的副作用和调用顺序，再列出遗漏。时间、随机数等不稳定因素应尽可能控制，只对业务确实允许变化的字段做归一化。

| 任务 | 修改前的相关用例 | 修改后 | 断言在表达什么 |
| --- | --- | --- | --- |
| 修复缺陷 | 因目标缺陷失败 | 通过 | 已确认的期望行为 |
| 保持行为的重构 | 在原实现上通过 | 继续通过 | 需要保留的现有行为 |

这张表能帮助发现一种常见混淆：刚补完测试就失败，却还把接下来的工作叫作“纯重构”。先判断失败来自测试写错、环境问题，还是需要单独修复的旧缺陷。

## 五、验收：按风险设计反例

让 Agent “对抗性测试”，要给它可判定的目标。例如连续点击两次提交，究竟允许产生两条记录，还是必须合并成一次？先明确预期，才能判断测试结果。

```text
对刚才的改动做一次以找出缺陷为目标的测试。
根据实际代码路径，挑选相关的异常输入、边界值、并发交错、
网络失败和错误假设；不适用的类别说明原因。

每个场景先说明预期结果或应保持的不变量，再执行验证。
在隔离的本地或测试环境中注入故障。
发现缺陷后做最小修复，并将有价值的复现保留为回归测试。
最终报告已验证、验证失败、无法验证的项目及实际运行结果。
```

例如搜索框会发出多个请求，可以控制返回顺序，让旧查询晚于新查询完成，再检查界面是否仍显示最新查询的结果。只断言“请求没有抛异常”，捕捉不到旧结果覆盖新结果的问题。

有些检查需要调用真实集成，有些需要浏览器操作；单元测试通过，不能代替这些层面的证据。反过来，也不必对每个纯函数都模拟整套网络。

Agent 写出的测试也需要审查。检查断言是否验证了需求，mock 是否绕开了出错路径，以及把实现改坏时测试是否会失败。测试运行成功只能说明当前这些检查通过了。

## 六、Code Review：固定范围，让问题可定位

“最后一次提交”可能只是一个大功能的最后一小步。审查前要说明是某个 commit，还是整个分支相对基线的变更。下面的模板用于一次聚焦缺陷的审查。

```text
只审查，不修改代码。本轮审查最后一次普通提交相对其父提交的差异。
若目标是合并提交或初始提交，先说明并确定比较基线。
报告审查对象与基线的 commit SHA，再阅读差异及必要的调用上下文。
本轮聚焦本次变更引入或暴露的安全、性能和逻辑缺陷，
忽略纯命名、格式与个人风格偏好。

每个问题给出文件路径、当前行号或紧凑行范围、触发条件、影响，
以及支撑判断的代码路径或复现方式。
区分已验证缺陷与待核实疑点，不把猜测写成确定结论。
没有可确认的问题就明确说明，并列出审查范围和未验证部分。
```

以下是虚构的审查记录格式：

```text
文件：src/search.ts:42
触发：先发出的查询 A 比后发出的查询 B 更晚返回。
影响：A 的结果覆盖 B，输入框与结果列表对应不上。
依据：回调直接写入结果，没有校验响应是否属于最新查询。
验证：控制两个请求的完成顺序为 B → A，断言页面仍显示 B。
```

若要审查整个 PR，应将模板第一行替换为明确的目标分支和功能分支，并记录所用的比较基线。上面的记录比“建议优化异步处理”更容易核查。行号必须来自被审查的版本；代码修改后，需要重新定位。

忽略风格是这轮审查的范围选择。团队约定、可维护性和必要文档仍可以由其他检查覆盖。Google 的指南包含这些维度，也提醒审查者阅读改动上下文，不能把它概括成“审查只看三类问题”。[参考：What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)。

## 七、长方案：让呈现方式服务于核查

比较多个架构方案、追踪复杂的数据路径时，HTML 可以提供分组、折叠和导航。一个小改动的结论，几行文字通常更容易读。原文第七条宜按内容选择，不能仅凭篇幅认定 HTML 更好。

```text
把这份需要分组阅读的方案整理为单文件 HTML，保存到约定的输出目录。
首页先展示结论与待决定事项，细节按需要使用标签页或折叠区域。
只有关系确实复杂时才画流程图；状态同时用文字和颜色表达。

保留关键文件定位、证据来源、验证结果和未确认的假设。
不引入构建流程，样式和必要脚本内联，不依赖外部 CDN。
确保窄屏可读、键盘可操作。
生成后在可用浏览器中检查显示与交互；若无法打开，报告文件路径和限制。
```

这里交付的是阅读用的文档。除非另有需求，不必给项目增加一条应用路由或一套前端依赖。把长段落原样塞进七个页签，信息负担也还在；应该先删去重复内容，把待决定的差异摆在一起。

无论用什么格式，交付说明都应让人找到这些证据：

| 要判断的事 | 应当看见的内容 |
| --- | --- |
| 改动是否符合需求 | 验收条件与修改文件的对应关系 |
| Bug 是否修复 | 同一复现用例在修复前后的结果 |
| 重构是否保留行为 | 原实现通过的基线、修改后的结果和覆盖缺口 |
| “已验证”意味着什么 | 实际执行的命令或操作、结果及未执行项 |
| 审查发现是否成立 | 具体版本、位置、触发条件与影响 |

七条提示词可以按场景分别收藏。每次使用时，先填清本次任务的输入、允许的动作和验收条件；交付时，再逐项核对留下的证据。
